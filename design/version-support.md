# Version support audit

Snapshot: 2026-10-07. Implementation issue: https://github.com/baseten/pixi-react/issues/3. Frozen upstream functionality base: `30cf1f86a590a1d8bb183a36b1887fa30e908d4e`.

## Decision and meaning of support

Keep the initial certification floors React **18.3.1**, Pixi **7.4.2**, and modern Pixi **8.2.6**. These are candidate certification targets. This audit does not certify a production adapter or widen advertised peer ranges. The frozen upstream feature baseline and modern dependency support are separate deliverables. The baseline package pins reconciler 0.31.0 and Pixi 8.2.6, uses React 19 types, and declares React >=19.0.0; that broad peer declaration is not evidence that later reconciler interfaces work.

Fresh registry metadata reports React **19.3.0**, reconciler **0.34.0**, and Pixi **8.22.0** as stable latest. [React's versions page](https://react.dev/versions) agrees with React 19.3; [Pixi's versions page](https://pixijs.com/versions) still says 8.21.0. The [8.22.0 tagged release](https://github.com/pixijs/pixijs/releases/tag/v8.22.0) and [npm metadata](https://registry.npmjs.org/pixi.js/8.22.0) agree on the newer Pixi release. The registry's legacy tag is 7.4.3, while the documentation page says 7.4.2. Preserve 7.4.2 as the accepted minimum; retain only the 7.4 patch line, with 7.4.3 a patch-promotion candidate rather than silently moving the floor.

React 16.14/17 final patch lines and older Pixi 7 minor epochs are future extensions, excluded from the initial advertised set. Fiber started in React 16.0 and hooks in 16.8 ([React history](https://react.dev/versions)); those facts explain possible extension work, not support. React <=17, Pixi <=6, canary/experimental React, and unvalidated backends are excluded.

## Evidence contract

The machine-readable [seed](compatibility/seed.json), [reproduction instructions](compatibility/README.md), and installed probes separate package metadata, source-level interface observations, and limited runtime/type evidence. No browser matrix or production adapter is implemented here. Every tuple remains `not-certified` until the later implementation and browser gates establish its advertised behavior.

The [baseline createRoot](../src/core/createRoot.tsx) supplies the ten-argument 19.0 shape; [createReconciler](../src/helpers/createReconciler.ts) casts a patched 0.28 declaration surface to the newer runtime. Do not carry that cast forward as proof. The installed runtime host-key diff and tagged source diff are retained in evidence. In published 0.33/0.34, the tenth argument means `onDefaultTransitionIndicator`, even though the arity remains ten; in tagged source `transitionCallbacks` follows it. Arity alone would miss this semantic ABI change. Tagged forks include disabled feature branches; published builds can omit them. Compare both and record what the installed build actually reads.

For every modern line the probe pins matching `@types/react` minor declarations independently, compiles scoped JSX/ref cases, and runs `its-fine` 2.1.1 context mount/update across two in-memory roots. `its-fine` reads private Fiber fields (`return`, `memoizedState`, `_reactInternals`) in its installed `dist/index.js`; its React peer declaration is insufficient assurance. The legacy tuple uses 1.2.5. Baseline 2.0.0 is metadata/source context, not an extra runtime-certified bridge tuple. The 2.1.1 Activity bridge is also not tested by a plain context bridge test.

## Adapter design rules and bounded matrix

Use separate React entrypoints/packages for the 18/0.29 and 19/0.31+ ABI families, keeping React types and reconciler dependencies isolated. Within React 19, use a shared implementation with narrow subclasses only where host/root contracts actually differ: 0.31 priority/commit behavior, 0.32 instrumentation and gated hooks, 0.33 root indicator/Activity/suspension, and 0.34 fragment/view-transition capabilities. These are candidate interface epochs, not four mandatory copies of a renderer. A missing hook exercised only by a feature remains a real incompatibility when that feature is advertised.

Use distinct Pixi 7 and 8 lifecycle/constructor/ticker strategies. Within Pixi 8, prefer capability branches and focused node strategies: Particle from 8.5, RenderLayer from 8.7, DOMContainer from 8.9, and event additions where exposed. Fixable regressions or visual default changes do not automatically justify a new class. Never use duck typing to treat Particle as Container; particle ordering/removal/destruction need their own implementation. Exclude 8.5.0's failing particle destruction tuple unless an explicit workaround is implemented and verified.

Future adapter peer ranges must end before the next unvalidated React minor (for example `>=19.0.0 <19.1.0` for a certified 19.0 epoch). Do not publish `>=19` or infer support from reconciler's `^19.x` peer. No range is newly advertised by this audit. Types must derive props/constructors/events from the consumer's installed Pixi version, with React JSX augmentation scoped to the selected adapter package; do not bundle a global union that exposes unavailable nodes or hooks.

Retain React 18.3.1 only and Pixi 7.4.x only for the legacy branch. For React 19 and Pixi 8, the seed enumerates each active minor's minimum/current patch plus the frozen Pixi 8.2.6 floor; patch duplicates are removed. Tests run independently on the two axes, not a patch Cartesian product. Certification CI should pair each React epoch with the Pixi floor/current and each Pixi boundary with one already-certified React epoch, then add cross-axis cells only for an observed interaction. This audit's component probes do not certify those combined cells.

Promote a patch only after checking registry integrity, tagged changes, targeted probes, installed consumer types, and the real renderer/browser lifecycle suite on the exact tuple. Keep the previous selected patch until replacement passes; never auto-promote a mutable `latest` tag. A new ABI boundary adds a sample and an explicit adapter decision. Regression exclusions include a reproducer and issue/owner disposition. Deprecation first marks the tuple in the manifest and announces the replacement; removing a supported floor or epoch requires owner review and a versioned release decision. No automatic scheduled monitoring is introduced.

## Recorded outcomes and remaining certification work

The final audit contains **44 tuples**: eight React epoch/patch tuples and 36 Pixi boundary/patch tuples. All isolated consumer programs compile. Basic React mount/update/unmount, context bridge updates, modern error callbacks, and 19.2/19.3 Activity visibility succeed in the minimal host. The 19.3 Fragment-ref negative probe captures `createFragmentInstance is not a function`; that expected missing-capability observation is retained even though the enclosing audit test succeeds. No claim about ViewTransition rendering follows.

Pixi 8.5.0 with TypeScript 5.6.3 fails the runtime probe on ParticleContainer destruction with `ParticleContainer.removeChildren() is not available. Please use ParticleContainer.removeParticles()`. The other 35 Pixi tuples pass the sampled scene/ticker/event-emitter/destruction probe. The runner intentionally exits nonzero for the 8.5.0 failure; manifest validation accepts only the recorded exact failure, not arbitrary nonzero exits. It does not change that tuple to supported. This audit does not locate the first fixed patch between 8.5.0 and sampled 8.5.2.

[Installed evidence](compatibility/evidence.json) records exact direct and resolved transitive packages, integrity strings, environment, failures, host-key deltas, selected declaration deltas and source hashes. [Tagged React surfaces](compatibility/tagged-react-surfaces.json) record root signatures and custom-host source deltas. Installed declaration hashes and selected overloads were compared for Application, Container, Sprite/Text, particles, ticker, pointer events and extensions; hashes show change, while the table classifies its meaning. Sources are frozen to named tags/package versions; mutable documentation-page disagreement is recorded above.

Remaining certification includes real React DOM-to-Pixi context and Activity bridging; asynchronous transitions/Suspense/error recovery; fragment refs/ViewTransition policy; constructor and event prop translation; full pointer propagation/hit testing; GPU resource disposal; shared globals/extensions; StrictMode remount; particle/render-layer/DOM nodes; and the explicitly selected WebGL/WebGPU browser backends. Canvas and other unvalidated backends remain excluded. The future design/CI tickets consume the seed and this list; they must not convert release-note evidence into passing renderer cells.
